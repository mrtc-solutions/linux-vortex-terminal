OVERVIEW

Getting Started with VORTEX

Understanding what VORTEX is

VORTEX (Verified Orchestration, Reasoning, Testing, Execution & eXperience) is a Linux-native, AI-assisted authorized cybersecurity and Linux operations workbench. It is designed for cybersecurity professionals, Linux administrators, researchers, and educators who work with real systems in controlled, authorized environments.

VORTEX is not a simulation. When authorized and permitted by its security architecture, it executes real commands on the real Linux host it is running on. Results reflect actual observed system state, not invented responses.

What is VORTEX designed to do?

  • Accept natural-language requests and translate them into typed, reviewed command plans.
  • Execute approved plans against the local Linux host through a Guardian-gated execution architecture.
  • Assist with Linux system administration, health checks, diagnostics, and authorized security assessments.
  • Maintain an append-only audit trail of every observed operation.
  • Provide honest reporting: unavailable tools, agents, or capabilities are reported as such — never fabricated.

How to start using VORTEX

  1. Open the New Task view (the ✦ nav item, selected by default).
  2. Type a natural-language request in the command bar at the bottom of the chat column, or click one of the quick-action buttons.
  3. Review the plan that appears in the Plan / Terminal Evidence panel. VORTEX shows you exactly what it intends to run before anything executes.
  4. Approve or reject the plan. Low-risk local diagnostics may auto-run under the Standard or Expert policy; all others wait for explicit approval.
  5. Observe real output streaming in the Live Output panel — this is actual stdout from the host.

How the main interface works

Chat Column

Where you type requests and see the conversational record. Editing a past message branches the conversation rather than rewriting history.

Plan / Evidence Panel

Shows the typed command plan with risk level, required tool, timeout, privilege, and Guardian decision. Commands only run after you approve them (unless policy permits auto-run for very low-risk diagnostics).

Live Output

Real stdout/stderr from executed commands, streamed from the Python sidecar. This is not simulated output.

Context & Host Panel

Displays the current task state, Guardian decision, agent participation, risk level, and live host environment details (distribution, kernel, privilege).

Quick-action buttons

The four quick-action buttons on the overview page send pre-written prompts: System health, Listening ports, Who am I, and Disk usage. These are safe, local-only diagnostic commands that demonstrate VORTEX's capabilities without requiring an engagement scope.

INTERACTION

Natural-Language Interaction

VORTEX understands ordinary English. You do not need to know exact command syntax. Describe what you want to know or do, and VORTEX will build a typed plan from your description.

Example requests

❯"Check my system health."
❯"Find what is consuming CPU."
❯"Check whether nginx is running."
❯"Show me open network connections."
❯"Analyze this authorized target."
❯"Find large files in my home directory."
❯"Show me who is logged in."
❯"Check disk space usage."

Information vs. execution

Some requests produce information only (a clarification or explanation) — no commands are executed. Others produce a command plan that requires your approval before any execution takes place.

i
VORTEX always shows you what it intends to run before executing anything. The plan card shows the exact command, required tool, risk level, network class, privilege requirement, and timeout. You remain in control at every step.

Conversations and branching

Every interaction is part of a persistent conversation. You can continue a thread across sessions. If you edit a previous message, VORTEX creates a new conversation branch rather than rewriting history, so the original record is always preserved.

Suggestion hints

When your request is ambiguous, VORTEX may offer suggestion chips — clickable hints for clarifying what you meant. These help narrow down the intent without requiring you to rephrase from scratch.

IMPORTANT

Real Command Execution

⚠ VORTEX executes real commands.

This is not a chatbot that generates hypothetical terminal output. When a plan is approved and authorized, VORTEX runs actual system commands through its Python sidecar on the real Linux host. The output you see is genuine observed stdout — not a simulation.

How execution works

  1. You submit a natural-language request.
  2. The Planner translates the request into a typed command specification: exact argv, required tool, risk level, privilege, network class, and timeout.
  3. The Guardian evaluates the plan against your configured risk policy, scope, and engagement. It can approve, require confirmation, or block the operation.
  4. If approval is required, the plan is displayed to you with a prominent APPROVE & EXECUTE button. Nothing runs until you click it.
  5. Approved commands are dispatched to the Python sidecar, which executes them with shell=False (no shell injection risk), streams stdout/stderr back to the UI, and records the observed output to the audit log.
  6. The analysis is based entirely on observed output. VORTEX reports what actually happened, including failures, errors, and missing tools.

What VORTEX will not do

  • VORTEX will not fabricate successful output for a command that failed or was never run.
  • VORTEX will not report a tool as available when it is not installed.
  • VORTEX will not bypass Guardian's risk controls or scope enforcement.
  • VORTEX will not modify its own source code based on AI outputs.
  • VORTEX will not silently install software without operator approval.
  • VORTEX will not send terminal output to external networks unless you explicitly configure a cloud provider and the privacy mode permits it.

Terminal (Real PTY)

The Terminal view provides a real Linux PTY (pseudo-terminal) on the host — a genuine interactive shell session. This is completely separate from the AI planning system. Keystrokes go directly to the host shell. AI-generated plans never enter the PTY unless you type them yourself.

PROTECTION

VORTEX Safety Architecture

VORTEX is built around a layered safety architecture. These mechanisms are not optional — they operate on every plan and execution request.

Planner

Translates natural-language requests into typed command specifications with explicit argv, tool, risk level, privilege, network class, and timeout. The Planner never executes commands — it only produces a plan for Guardian review.

Guardian

The single authority for execution decisions. Guardian evaluates every plan against the configured risk policy, engagement scope, and execution authority before any command runs. It can approve, require operator confirmation, or block an operation entirely.

Orchestration

Coordinates the overall workflow from request to analysis. Orchestration routes requests through the Planner, Agent Council, Guardian, and execution layers, maintaining task state throughout.

Agent Council

A set of AI agent adapters that provide advisory input (reconnaissance suggestions, analysis hints) to the Planner. Agents never execute commands directly — they are advisory only and never bypass Guardian. Missing agents are reported as UNAVAILABLE, not silently skipped.

Risk Policy

Three configurable profiles: Safe (always confirms), Standard (may auto-run very low-risk local diagnostics), Expert (broader auto-run, never bypasses Guardian or audit). Set in Settings.

Engagements & Scope

Active tools such as nmap require a declared engagement with an explicit target, authorization reference, and expiry. Scope is revalidated at execution — a plan cannot execute against a target outside the declared scope.

Tool Registry

VORTEX maintains a catalog of known security and administration tools. Each tool is probed on the real host. If a tool is not installed, it is reported as ABSENT or UNAVAILABLE — plans requiring that tool are blocked until it is installed by the operator.

Observed Evidence

Execution output is captured as observed evidence. The audit trail records what actually happened, not what was expected. Evidence digests are included in reports; raw output is not retained by default.

Verification

After execution, VORTEX reports the number of commands that produced observed output vs. the total planned. This makes partial failures visible rather than hidden.

Task Engine

Every request becomes a durable VTX task. Tasks persist through restarts; interrupted work can be inspected, resumed, or deleted from the Tasks view.

STOP ALL

The red STOP ALL button in the topbar immediately cancels all active VORTEX-controlled operations and kills all open PTY sessions. It does not affect processes you started independently on the host.

Audit Logging

An append-only local audit log records every operation with timestamps and outcome digests. The VERIFY AUDIT CHAIN button in the Activity view checks the integrity of the chain. Logs are local-only by default.

Offline Mode

Blocks outbound network plans and external model calls. Local tools and memory remain available. Toggle in Settings → Offline mode, or start VORTEX with the offline flag.

Privacy Mode

Three levels: Local-only (default — nothing leaves the host), Hybrid, Cloud. Terminal output is never sent externally unless you explicitly configure a provider and set privacy mode to Hybrid or Cloud.

Lab Mode

Marks the workspace as an authorized laboratory environment. External targets still require an engagement scope — Lab Mode does not bypass scope enforcement.

Sandbox

VORTEX includes sandbox capabilities for isolated execution. Sandbox status is visible in ./vortex sandbox --json.

HONEST TOOLING

Tool Availability

VORTEX does not pretend that tools are installed when they are not. Every tool in the catalog is probed on the real host at startup and on demand. If a required tool is missing, the plan that depends on it will be blocked and the tool's status will be reported accurately.

Tool status meanings

INSTALLED The tool was found on the host PATH and probed successfully. It may be used in approved plans.
ABSENT The tool is not installed on this host. Plans requiring it will be blocked. Install it through your system package manager or the DEPENDENCIES panel.
UNAVAILABLE The tool exists in the catalog but cannot be used in the current context (e.g., missing dependency, policy restriction, or no active engagement).
BLOCKED The tool is explicitly blocked by policy or scope — for example, active offensive tools require an engagement scope with an explicit authorization reference and expiry.
REQUIRES AUTHORIZATION The tool requires an active engagement scope before it can be planned. Create an engagement in the Engagements view first.
NOT IMPLEMENTED The adapter for this tool exists in the catalog but is not yet fully implemented. It will be available in a future version.

Checking tool status

Open the Tools view from the sidebar to see all catalog tools and their current host status. Click REFRESH PROBES ↻ to force a fresh probe. Click RESCAN PATH to discover any new tools you have installed since VORTEX started. Click MISSING to open the Dependencies panel with install proposals for absent tools.

Host PATH tools

When Host tool access is enabled in Settings, VORTEX can also plan commands for tools discovered on your system PATH (including tools installed on Kali Linux) that are not in the built-in catalog. Guardian, scope enforcement, and shell=False still apply to these tools.

SUPPORT

Troubleshooting

"A tool says UNAVAILABLE"

Open the Tools view and click REFRESH PROBES ↻. Check whether the tool is installed on the host (which <tool> in the Terminal view). If it is missing, click MISSING to open an install proposal. If it requires an engagement, create one in the Engagements view.

"A command did not execute"

Review the error message shown in the plan card or toast notification. Common causes: the required tool is absent, the plan was rejected by Guardian due to policy or scope, the timeout was exceeded, or the command produced a non-zero exit code. Check the Activity view for the full operation record.

"An AI agent is unavailable"

Open the Agents view. VORTEX honestly reports which agents are installed and available on this host. An UNAVAILABLE agent means its CLI executable was not found. VORTEX never pretends an agent responded when it did not. Click the install proposal button for operator-controlled installation instructions.

"A task is still running"

Open the Tasks view to see running and interrupted tasks. You can pause the current task using the PAUSE button in the plan card, or use STOP ALL in the topbar to immediately cancel all active operations and sessions.

"I need to stop everything immediately"

Click the red STOP ALL button in the top-right toolbar. This cancels all VORTEX-controlled operations and kills all open PTY sessions. It calls /api/control/stop-all and reports how many operations were cancelled and sessions killed. Use this if a plan is executing and you want to halt it immediately.

"The application reports an error"

Toast notifications at the bottom right show immediate errors. The Activity view contains the append-only operation history with status and command records. The System view shows live health probes for backend components. For deep diagnostics, run ./vortex doctor --json from the command line.

"The backend appears offline"

The top-right status indicator shows BACKEND ONLINE or OFFLINE. If offline, the Python sidecar may not be running. Start it with python3 backend/vortex_backend.py or npm run preview. In Electron mode, the sidecar is managed automatically.

"First-run checks failed"

The first-run setup window appears when required components are missing. You can skip it and still use VORTEX — optional components simply remain unavailable. Use the DEPENDENCIES button in the topbar or Tools view to review and install missing items.

COMMAND LINE

CLI Reference

VORTEX provides a CLI entry point (vortex / ./vortex) for diagnostics and administration outside the GUI. The following commands have been verified against the current codebase.

./vortex --help Show the CLI help message and available subcommands.
./vortex doctor --json Display host environment information: distribution, kernel, architecture, privilege level, container context, and more. JSON output for scripting.
./vortex health --json Run live health probes on all backend components and report their status. JSON output for scripting.
./vortex tools List the tool catalog with current host probe status (installed / absent / blocked).
./vortex agents --json List configured AI agent adapters and their availability on this host.
./vortex deps --json Show missing dependencies from the catalog with installation proposals.
./vortex sandbox --json Report sandbox capability status for this host.
./vortex db integrity Verify the integrity of the local VORTEX database.
i
Only use CLI subcommands that appear in ./vortex --help. Do not rely on subcommands not listed there — they may not be implemented in your installed version.
GLOSSARY

VORTEX Terminology

Agent
An AI adapter that provides advisory input to the Planner. Agents are consulted but never directly execute commands. They are part of the Agent Council.
Agent Council
The collection of configured AI agent adapters. The Council advises the Planner; Guardian makes all execution decisions independently of Council output.
Orchestration
The workflow layer that coordinates requests through the Planner, Agent Council, Guardian, and execution engine, maintaining task state throughout.
Planner
The component that translates natural-language requests into typed command specifications with explicit argv, tool, risk level, privilege, network class, and timeout.
Guardian
The single authority for execution decisions. Evaluates every plan against risk policy, scope, and engagement before any command is dispatched.
Risk Policy
A configurable profile (Safe / Standard / Expert) that determines which operations Guardian auto-approves vs. requires operator confirmation.
Engagement
A declared authorization scope for active security operations. Contains the target, authorization reference, owner, expiry, and excluded targets. Active offensive tools require an engagement.
Scope
The set of targets permitted within an engagement. Scope is revalidated at execution — commands cannot run against out-of-scope targets.
Tool
A system binary or command that VORTEX can include in a plan (e.g., nmap, ps, df, ss). Tools are probed on the host and reported honestly as installed, absent, or blocked.
Execution
The act of dispatching an approved plan's commands to the Python sidecar, which runs them with shell=False and captures observed stdout/stderr.
Evidence
The observed output from executed commands. Evidence is captured in the audit log with a digest. Raw output is not retained by default.
Verification
Post-execution summary of how many commands produced observed output vs. the total planned. Makes partial failures visible.
Task
A durable unit of work created for every request. Tasks persist through restarts and can be inspected, paused, resumed, or deleted.
Session
A real PTY (pseudo-terminal) session on the Linux host, managed through the Terminal view. Independent of the AI planning system.
Sandbox
An isolated execution environment for running commands in a controlled context. Sandbox capabilities depend on the host configuration.
Audit
The append-only local log of all operations and their observed outcomes. Verifiable with VERIFY AUDIT CHAIN in the Activity view.
Offline Mode
A setting that blocks outbound network plans and external model calls while keeping local tools and memory available.
Privacy Mode
Controls whether data leaves the host: Local-only (default), Hybrid, or Cloud. Terminal output never leaves without explicit configuration.
Lab Mode
Marks the workspace as an authorized laboratory. External targets still require an engagement scope.
